# T26 — Scale proof: real numbers on real monorepos

**Blocked by:** T25 · **Effort:** medium · **Phase:** B
**Fills:** `docs/05-PERFORMANCE.md`. Produces the gate for Phase D.

## Why this exists
"Works on my sample project" is what every portfolio project says. Numbers from
a 300k-file repository are a different claim, and they are only worth making if
they are real. This task also produces the measurement that decides whether
Phase D (viewer culling) gets built at all.

## The rule that governs this task
Every number published here must be reproducible by a command written in
`docs/05-PERFORMANCE.md`, on a named machine, against a named repo at a named
commit. A number without those three things does not get written down.

This project has already had one round of confident-looking benchmark figures
that were never measured. That is why this rule exists and why it is stated
this bluntly.

## The corpus
Pin a **commit sha** for each, not a branch. A branch moves and the numbers stop
being reproducible.

| Tier | Repo | Approx files | Notes |
|---|---|---|---|
| medium | `pallets/flask` | ~1k | already used elsewhere |
| large | `python/cpython` | ~10k | deep history |
| very large | `torvalds/linux` | ~80k | C-family, complexity-only tier |
| extreme | `chromium/chromium` **or** a synthetic 250k-file tree | 250k+ | see below |

Chromium is enormous to clone (tens of GB). It is acceptable, and should be
stated plainly, to substitute a **synthetic** tree at the extreme tier —
generated by replicating a real repo's structure N times — provided the results
label it as synthetic and do not imply Chromium was tested. A labelled synthetic
benchmark is honest; an unlabelled one is a lie that will be caught.

`scripts/fetch_testrepos.sh` clones each at its pinned sha with
`--filter=blob:none`, into `.testrepos/`, and writes the manifest T23 consumes.

## What to measure and publish
Per repo, per tier:

- Cold full build: wall time, peak RSS, output `city.json` size (raw + gzip)
- Warm full build (`--force-full` with a hot cache)
- Incremental build after a one-line edit to one file
- Incremental build after a `git pull` bringing 20 commits
- Stage breakdown at each of the above (T23's harness does this)
- Viewer: time to first frame, and fps at idle orbit — **on the largest city
  that loads at all**

Also record, because they are the interesting failure points and reviewers will
ask about exactly these:

- Peak memory, and whether anything was swapped
- The largest tier where the browser successfully loaded the `city.json`, and
  what happened at the tier above it (OOM? multi-minute parse? blank screen?)
- Whether `json.dumps` of the whole document became a memory problem before
  rendering did

## The honest-failure requirement
It is likely something breaks at the extreme tier. **Publish that.** A section
reading:

> At 250k files the build completes in N minutes but `city.json` is 1.4 GB, and
> the browser tab runs out of memory before the first frame. The bottleneck is
> document size, not render performance. Fixing it needs a streaming or chunked
> format, which is out of scope here and recorded as an open question.

is a *better* artifact than a table where everything is green, because it proves
the numbers were actually run and it shows the author knows where the wall is.
A benchmark table with no failures in it is a benchmark nobody ran hard enough.

## The Phase D gate — the decision this task must produce
Write this conclusion explicitly at the end of the section:

> **At the largest tier that loads, the binding constraint is `<analysis |
> document size | render>`, at `<N>`. Phase D (viewer culling/LOD) is therefore
> `<SCHEDULED because the renderer is the wall | NOT BUILT because the wall is
> elsewhere>`.**

If the wall is analysis time or JSON size — the likely outcome given the viewer
already holds 61 fps at 1272 files while the build takes ~34 s — then Phase D is
recorded in `STATUS.md` as `WONTFIX: measured, not the bottleneck`, with a link
to this section. That is a successful outcome. `docs/05-PERFORMANCE.md:66`
already instructed exactly this; this task is what discharges it.

## Acceptance criteria
1. Every published number has: machine spec, repo, pinned sha, command, date.
2. `scripts/fetch_testrepos.sh` reproduces the corpus from scratch on a clean
   machine.
3. At least one measured failure or hard limit is published with its cause.
4. The Phase D gate conclusion is written, one way or the other.
5. README's performance claim is **one sentence** citing the doc, not a copied
   table. Tables in READMEs go stale silently; a pointer does not.
6. No number appears in any commit message, README, or write-up that is not in
   `docs/05-PERFORMANCE.md`.

## Default if ambiguous
- If a tier cannot be run on the available hardware, say so and skip it. An
  omitted tier with a stated reason is fine; an estimated one is not.
- Do not tune the analyser to make a benchmark look better and then publish the
  tuned number as if it were the default configuration. Publish defaults.
